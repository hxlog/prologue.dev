# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A content-first personal blog (Chinese, `prologue.dev`) built on **Next.js 16 App Router + Turbopack, React 19, Tailwind CSS v4**, on an **in-repo filesystem content layer** (no Contentlayer). It doubles as the **source of truth for a public starter template** — see the "Template publishing" section, which is the least obvious part of this codebase.

## Commands

```bash
corepack enable        # once per machine — makes `yarn` resolve to the pinned Yarn 4
yarn install           # install dependencies (node-modules linker)

yarn dev               # build search index + next dev --turbopack
yarn build             # same prep, then next build --turbopack
yarn start             # serve production build
yarn lint              # eslint (flat config in eslint.config.mjs)

yarn publish           # build the template snapshot locally (dry run — no push)
yarn publish -- --push # force-push template to hxlog/prologue-blog-template
```

CI (`.github/workflows/ci.yml`) runs `lint` and `build`.

## Package manager

**Yarn 4 (Berry)**, pinned by `packageManager` in `package.json` and driven through Corepack: run `corepack enable` once per machine, after which `yarn` resolves to the pinned release anywhere in this repo. `yarn.lock` is committed; there is no `package-lock.json`. `.yarnrc.yml` sets `nodeLinker: node-modules` — Next.js/Turbopack and Vercel both need a real `node_modules` tree, so Plug'n'Play is not an option here.

CI enables Corepack before every job and installs with `yarn install --immutable`, which fails instead of rewriting `yarn.lock` (the `npm ci` equivalent).

Two dependencies are deliberately not on `latest`, both because of peer ranges rather than preference:

- **`eslint` on the latest 9.x** — `eslint-config-next@16` pulls in `eslint-plugin-import`, `eslint-plugin-react` and `eslint-plugin-jsx-a11y`, whose peer ranges stop at `^9`. ESLint 10 is a real peer conflict there (npm fails with `ERESOLVE`), so 9.x is the conflict-free latest.
- **`typescript` on the latest 6.0.x** — `eslint-config-next` imports `typescript-eslint`, which `require`s `typescript` at lint time even in a JavaScript project, so it is a real devDependency (npm used to install it as a transitive peer; Yarn does not). Its peer range is `>=4.8.4 <6.1.0`, and TypeScript 7 is out but unsupported.

Everything else is on `latest` as of the migration. `yarn up -i` is the interactive upgrader; `yarn up tailwindcss @tailwindcss/postcss` picks up the one patch release that Yarn's default 24-hour `npmMinimalAgeGate` (supply-chain quarantine of freshly published versions) held back.

## Content layer

There is **no Contentlayer**. `src/lib/content/` reads `data/content/**` with `fs` and produces the same document shape Contentlayer2 emitted:

- `load.js` — the loader. Reads frontmatter, computes `readingTime`/`headings` eagerly; `body.html` is **lazy and async** (Shiki is the whole cost). `getPosts()`, `getPages()`, `getPost()`, `getPage()`, `getBodyHtml(doc)`, `getAllPostsWithBody()`.
- `pipeline.js` — the one markdown renderer (unified: remark gfm/math/gemoji → rehype katex/slug/figure/mermaid-pre/shiki/stringify). Plugin order and options are copied from the old `contentlayer.config.js` and verified byte-identical against it. **Do not add options to `remarkRehype` or `rehypeStringify`** — Contentlayer called both bare, and raw HTML blocks collapsing to their text content is load-bearing for three posts.
- `slug.js` — the slugger + heading extractor (F2 fix: anchors and ids now come from the same pass).
- `index.js` — the public API, and **the only file carrying `import "server-only"`**. `standalone.js` is the same surface without the guard, for plain `node scripts/…`.

**The exports are functions, not arrays, and the name says so.** `getPosts()` replaces Contentlayer's `allPosts` constant. The markdown is read with `readFileSync`, which no bundler watches, so a module-scope constant freezes at first evaluation and a content edit in `next dev` keeps serving stale HTML. `load.js` therefore checks an mtime+size signature of the tree on each access (~1.2 ms over 64 files vs ~103 ms to re-parse) and re-reads when it changes; the check is skipped entirely under `NODE_ENV=production`. See `current()` in `load.js` for the ENOENT/EBUSY reasoning. Do not "simplify" this back into a constant, and do not cache the returned array across a render.

Frontmatter is validated **loudly**: a mistyped `draft: "false"` (which is what Obsidian's Properties UI writes when the property type is Text) fails the build naming the file and field, where Contentlayer2 warned and silently skipped the document. Pages (`data/content/pages/`) need only `title` and `description`; posts also need `publishDate`. **A page's body is plain markdown and raw HTML in it is dropped, not escaped** — the pipeline calls `remarkRehype`/`rehypeStringify` bare, so an `<img class="...">` in `about.md` disappears. Anything on a page that needs styling, like the author avatar, is a frontmatter field the page template renders (`avatar:`, opt-in); see `docs/CONTENT.md`.

`src/lib/microblog.js` reads the one non-post dataset: `data/microblog.yaml`, a list of `{ date, content }` entries. It parses with the `yaml` package and returns `getMicroblog()`. Entry ids are **derived, not stored** — `mb-<YYYYMMDD>-<array index>` — so they are stable only as long as the list order is; inserting an entry in the middle renumbers every later one and breaks `/microblog#…` anchors and RSS guids at once. `getMicroblog()` is a function for the same staleness reason as the loader.

`data/links.yaml` (friend links) is read inline by `src/app/links/page.js` with the same parser. `data/static/` no longer exists: the site's static assets are a **real tracked directory** at `public/static/**`, served directly by Next at `/static/*`. It is deliberately not a symlink or junction to a directory under `data/` — Next's static-copy step refuses to copy a directory into itself, which fails the build on Vercel ("Cannot copy '../data/static' to a subdirectory of itself").

`data/sitemetadata.js` and `data/tagLabels.js` are **hand-written** modules, not generated. They are read by *client* components (navbar, footer, the two modals, tag chips), so their values have to be in the JS module graph and shipped to the browser — a browser cannot import markdown, and an `fs` read at render time cannot reach a Client Component either. That is why they are `.js` and why they are committed rather than gitignored.

`data/headerNavLinks.js` is a `.js` file for the same client-component reason.

## Markdown pipeline & Mermaid

Configured in `src/lib/content/pipeline.js` (remark: gfm, math, gemoji; rehype: katex, slug, custom `rehype-figure`, custom `rehype-mermaid-pre`, shiki, stringify). The custom rehype plugins live in `src/components/`.

`rehype-mermaid-pre` converts ```mermaid code fences into `<pre class="mermaid">` blocks. Mermaid is then rendered **two different ways** depending on the consumer — keep both in sync if you touch either:

- **On the web**: `OptimizedHTMLRenderer` (`src/components/optimized-html-renderer.js`) parses the rendered HTML, routing `<img>` to `next/image` and `<pre class="mermaid">` to the client-side `MermaidBlock` (dynamic-imports `mermaid`, theme-aware); everything else goes through `dangerouslySetInnerHTML`. `MermaidBlock` **replaces** the `<pre>` with a `div.mermaid`, so a rendered page has 0 fences and 1 SVG — anything asserting on fence count is asserting on what is supposed to be gone.
- **In feeds**: `src/lib/feed/mermaid.js` + `mermaid-shared.mjs` rewrites the same `<pre>` blocks into hosted `mermaid.ink` PNG `<img>` URLs (pako deflate + base64url encoding), since RSS readers strip inline SVG.

**The web renderer forces `look: "classic"`, and that is a design requirement, not a preference.** Mermaid 12 changed the flowchart default to `look: "neo"`, which paints a drop-shadow halo `filter: drop-shadow(1px 2px 2px rgba(185,185,185,1))` plus a gradient stroke around *every* node and cluster. Under this site's flat hairline surfaces that reads as a second, duplicated elevation — the "why is the mermaid diagram dirtier than on GitHub" report. `MermaidBlock` initializes with `look: "classic"` (the flat render GitHub shows), passes `--font-sans` in as `themeVariables.fontFamily` so diagrams use the site's type stack instead of Trebuchet MS, and `globals.css` keeps an `!important` `filter: none` reset over `.mermaid svg [data-look="neo"]` as a version-proof backstop. Measured after the change: 0 elements with a computed `filter` across three diagrams on `/blog/evaluating-ai-data-labeling-accuracy`, versus every node rect before. Do not "restore" the neo look without a screenshot comparison against the flat surfaces.

## Feeds (RSS / Atom / JSON)

Routes: `src/app/rss`, `src/app/atomfeed`, `src/app/jsonfeed`. All three call `createFeed()` in `src/lib/feed/build-feed.js`, which builds a single `Feed` instance; each route only picks the serializer (`rss2`/`atom1`/`json1`). Per-item HTML is produced by `buildFeedContent()` in `src/lib/feed/content.js`, which promotes block math (`math[display="block"]`), absolutizes URLs, and normalizes images. It used to also strip a KaTeX presentation layer; formulas are native MathML now, so that pass is gone. Format-specific fixes the `feed` library can't express (inject `<dc:creator>`, JSON Feed per-item `image`) live in `src/lib/feed/finalize.js` — note `imageByUrl()` is a function, not a module constant, for the same staleness reason as the loader. URL helpers in `src/lib/feed/urls.js` derive absolute URLs from `siteMetadata.siteUrl`; `coverImageUrl()` falls back to the `/og` generator when a post has no `image`.

Feed XML is produced by `getFeedXml(format)` in `src/lib/feed/cached.js`, which wraps `createFeed()` in `'use cache'` + `cacheLife({ stale: 600, revalidate: 3600, expire: 86400 })`. Both halves matter:

- **The cache, because the builder is expensive.** `createFeed()` renders all 64 post bodies through Shiki before any format can be serialised. It used to run per request (the builder awaited `io()` for a clock read, which forced the route dynamic), so every reader poll paid the whole corpus. The three feed routes are now `○`, and the stale window matches the `s-maxage` they already send so the CDN and the function agree on how old a feed may be.
- **The clock argument, because the timestamp has to come from somewhere.** `createFeed(now)` takes the date from the caller: a `'use cache'` scope is allowed to read the clock, a request handler that must stay static is not. Do not put `new Date()` back inside `createFeed()` without moving the read into a cache scope.

The `Cache-Control` header is still `s-maxage=600, stale-while-revalidate=86400`: content only changes on deploy, so a 10-min edge window is safe and keeps readers off the function path entirely.

## Template publishing (important)

This repo is mirrored to a public template (`hxlog/prologue-blog-template`) **without the author's posts, maintainer-only files, or personal assets**. On every push to `master`, `.github/workflows/publish-template.yml` runs `yarn publish`, which executes `scripts/publish-template.mjs`. That script:

1. Creates a detached git worktree of `HEAD`.
2. `applyStarterTemplate()` deletes maintainer-only paths (`template/`, `docs/`, `.idea/`, `scripts/`, the publish workflows), wipes `data/content/*` and `public/static`, then copies the starter overrides from `template/`.
3. Force-pushes the snapshot to the template repo (auth via `TEMPLATE_REPO_TOKEN` secret, falling back to `gh auth token`).

**Implications when editing:**
- The `template/` directory is the starter's overrides — not used by this site, but *is* what template users receive. Edit it when you intend to change the template's default content/assets.
- Anything new added for the template must be placed under `template/` (or whitelisted in `applyStarterTemplate`), or it won't ship. `ensureTemplateInputs()` asserts the required ones exist, so a missing file fails the publish rather than shipping a broken clone.
- Template-critical files that live in `src/` or `scripts/` are copied explicitly by `applyStarterTemplate`: `scripts/build-search-index.mjs` — the only script the shipped `package.json` invokes. **Anything the shipped `dev`/`build` scripts invoke must be in that list**, or a fresh clone fails on its first command.
- `template/data/{microblog.yaml,links.yaml,sitemetadata.js,headerNavLinks.js,tagLabels.js}` and `template/public/static/` are required inputs; five `src/` files import the two `.js` data modules, so a template without them does not build.
- Locally, `yarn publish` builds and inspects the snapshot under `.tmp/` (gitignored) and stops; `yarn publish -- --push` is what force-pushes. CI passes `--push`.

## Design system

Semantic tokens live in `src/app/globals.css` under `@theme inline`, mapped to CSS variables that flip under `.dark`.

**Brand primitives: lavender `#b5b5e5`, pink `#e6c9d9`, warm stone `#a8a29e`** (`--color-brand-lavender` / `-pink` / `-stone`) are the historical source swatches and carry no semantics. The pastels actually painted are `--accent-pastel #c9cdf5` / `--secondary-pastel #f7d4e6` / `--sky #b4e0ec`. None of them are consumed for text; everything reads a semantic token.

**v3 "ice lavender" palette.** v2 ("cool paper") moved the neutrals from warm stone to cool slate; v3 pushes the accent one more step towards light, because the purple still read as heavy:

- **Light mode**: background `#f7f8fc`, ink `#2f3446` (11.6:1), surfaces `#ffffff` / `#f1f3fa` / `#e5e8f3`, `--muted #5d6579` (5.49:1), `--faint #767e92` (3.83:1 — allowed below AA because it only carries metadata that appears elsewhere). Accent `#6a6fcd` (**4.15:1** on the page, 4.40:1 on a white card), secondary `#b85680` (4.23:1). **The accent is deliberately below AA for small text.** It is used for **chrome only** — eyebrows, the active nav pill, card-title hover, border and gradient tints — where a miss costs nothing; the brief asked for a visibly lighter, cooler lavender and this is the approved trade. Two things never use it: a *fill carrying a label* (buttons: `--accent-strong`, 5.35:1 with white) and *body copy* (prose links and inline code: 5.04:1 / 5.01:1 on the page, because 18px regular is not "large" per WCAG). Hover on a body link goes lighter, not darker, matching the rest of the site.
- **Dark mode**: background `#14161d`, surfaces `#1c1f28` / `#242832` / `#2f3441`, ink `#eef0f7` (15.9:1), `--muted #b3b8c6` (9.1:1), `--faint #979db0` (6.7:1). Accent `#ccd0f8`, secondary `#f4cede`. `--border-strong` is `0.14`, not `0.18`: the brighter hairline was the second half of the "dark hover is too white" report.
- **A fourth hue, sky `#b4e0ec`** (`--sky`), is allowed ONLY inside gradients and the cursor glow. It never carries text or a control, so it cannot fail contrast.
- `--accent-strong` is the *darker* ink in light mode and the *lighter* pastel in dark mode: "strong" means "more contrast against the current background".
- `--on-accent` is white in light mode and `#1b1d26` in dark, because white on pale lavender fails in dark mode.
- Gradients: `--gradient-brand` is the **fill**, and it is now **three stops** (lavender → `#dff0f9` sky → pink) so a brand rule reads as a gradient rather than a two-colour ramp; `--gradient-brand-text` is the **text** gradient (light mode uses the inks); `--gradient-aurora` is the lavender→sky→pink wash behind the homepage hero (`.hero-aurora`, CSS-only — no image asset; its section is `overflow-x-clip` because the wash bleeds 30% past each side and would otherwise be real horizontal overflow). `bg-clip-text` must use `--gradient-brand-text` or the headline washes out.

One ladder covers type (`--text-caption/sm/base/lead/title/h2/h1/display`, each with its own line-height), radii (`control/card/panel/pill`), containers (`page/archive/read`), shadows (`card/card-hover/pop`, all tinted by `--shadow-tint`) and motion (`--ease-out-expo`, `--duration-instant/fast/base/enter/slow`). Prefer these over arbitrary values; a new arbitrary radius or duration should be a token.

The v3-style `tailwind.config.js` (loaded via `@config`) holds only `darkMode: ["class"]` + the typography plugin.

**Fonts: system only — the site makes ZERO font requests.** There is no `next/font` import anywhere. `--font-sans` is the latin faces followed by the platform CJK stack (PingFang SC / Microsoft YaHei / Noto Sans CJK), and it is the *only* family: `--font-serif` no longer exists and the three `font-serif` call sites (home lead, page description, post description) were folded into it. `--font-mono` is the platform mono (ui-monospace / Menlo / Consolas) and is used only by code content and `.copy-field`.

Two rounds got here, both by measurement. First the two `Noto_*_SC` families: 101 unicode-range slices each, **33 woff2 / 1.99 MB** on one Chinese article, and because text paints with the fallback and repaints as slices arrive, every arrival was a new LCP candidate (p75 13.2 s on a 196 KB page). Then the last latin mono (`JetBrains_Mono`, 40 KB) went too — `display: "swap"` still painted code blocks in the fallback first and swapped them, the same mechanism, on every code-heavy article. **Do not reintroduce a webfont without re-measuring LCP — the swap repaint is the mechanism, not the byte count.**

Formulas are **native MathML**: `rehype-katex` runs with `output: "mathml"`, the post route no longer imports `katex.min.css`, and `src/lib/feed/content.js` no longer strips a KaTeX presentation layer (there is none). Measured on a 10-formula post: **0 font requests** and 0 `span.katex-html` nodes, versus 1-3 woff2 / 10-25 KB before. That was the last webfont on the site, so "zero font requests" is now literally true rather than "except math". The tradoff is deliberate: MathML is set by the platform math font, so a formula's glyphs are no longer identical across OSes. The alternative — keeping KaTeX — costs a font fetch per math article plus a katex stylesheet in every article's critical CSS. If formula fidelity ever becomes a requirement again, this is the exact line to revert (plugin option + `import "katex/dist/katex.min.css"` in the post route) and the numbers above are the baseline to re-measure against.

**Typography overrides must map the whole `--tw-prose-*` family.** `@tailwindcss/typography` only swaps its defaults under `.prose-invert`, and this site toggles dark mode with a class on `<html>` — so leaving the defaults in place made `--tw-prose-headings` (its `#111827`) paint every H1/H2 near-black on the dark background. The `.prose` block in `globals.css` now points headings, bold, links, quotes, captions, bullets, code, table borders and their `-invert` counterparts at semantic tokens. Add a new prose rule *after* the token-mapping block, not before.

**No animation library.** `framer-motion` is not a dependency. The root `<MotionConfig reducedMotion="user">` alone pulled it into every route's shared chunk to honour an OS preference; reduced motion is handled in CSS, the tab-panel cascade is the `.reveal-rise` class, and the TOC marker is `.toc-pill` (drawn inside the active row, because rows wrap to different heights and a single sliding pill would need layout measurement).

**Component classes** live in a `@layer components` block in `globals.css` so markup reads as structure, not as twenty utilities: `.shell` (page container), `.sticky-below-nav` (sidebar `top` that clears `--nav-height`), `.skip-link`, `.btn` / `.btn-primary` / `.btn-ghost` / `.btn-icon`, `.input`, `.nav-item` (a **pill**; active state via `[data-active]` / `[aria-selected]` / `[aria-current]`), `.card` / `.card-interactive` / `.card-spotlight`, `.chip` / `.chip-more`, `.eyebrow` / `.section-label`, `.link`, `.text-gradient`, `.glass-header`, `.hero-aurora`, `.reveal-rise`, `.toc-pill`, `.modal-panel`, `.copy-field`.

Two shape decisions are deliberate. **Cards are flat at rest** — the elevation is an inset hairline ring (`--shadow-card: inset 0 0 0 1px var(--border)`), so nothing is lifted until the pointer arrives. Hover is a 2px lift plus **one twin-outline system**: `.card-spotlight::before` paints a 1px conic rim whose three colour sectors rotate to the pointer, `.card-spotlight::after` paints a soft pointer-tracked glow, and the second outline is a 1px inset hairline (the `inset` layer of `--glow-shadow`) drawn over the neutral one.

`conic-gradient` in three 120° sectors — sky, lavender, pink — with 6 % blends, shown only as its 1px border by masking the content box and the full box and excluding the first from the second. The `from` angle is `--spot-ang + 90deg`, so the first sector boundary lands at the pointer and the hues rotate around the card as the cursor moves. Measured on a text-free 397×208 probe with the production CSS: pointer at the centre (`from 90deg`) puts **pink on the top edge, sky on the right and bottom edges, lavender on the left**; pointer at the top-left (`from -61deg`) puts **sky on top, lavender on the right, pink on the bottom-left**. All three hues are on the rim at once, at 0.6 (light) / 0.35 (dark) alpha of saturated pastels — pale hues at high alpha composite to "tinted paper", while a saturated one at low alpha keeps real chroma without darkening the card.

The glow is two concentric radials at `--spot-x` / `--spot-y` (lavender core, sky halo), light 0.24 / 0.12 and dark 0.07 / 0.033. It is deliberately not a third hue: the rim already carries all three, and a tri-hue glow blends to lavender under the text. Measured with the probe: light hover **mean L 0.967 against 0.999 at rest** (max C 0.090, 24 % of the card chromatic — still "very light"), dark hover **mean L 0.275 against 0.241** (+0.034, the faint-halo target), and a real card's title computes the same colour hovered and at rest in both themes.

This replaced the earlier conic "aurora" ring and the v4 band wash + 1px rim + three-blob glow — both read as one tinted surface rather than as three colours, and the twin-outline + glow is the version that keeps the card white. Removed with them: `.card-ring` (and its `<span>` in `card.js` / `friendlinks.js`), `--aurora-*` (triplets and ellipse radii), `--ring-*`, `--sheen-hi`, the `spot-breathe` keyframes and `--spot-a`. The `--glow-*` tokens are RGB **triplets** now so one triplet powers the rim, the hairline and the glow at three alphas.

**Tag pills reuse the card rim in a cheaper form ("stardust").** A 24px pill cannot carry the twin-outline + glow pair, so at rest `.chip` is a 6 % three-hue wash plus a 1px lavender hairline (`--chip-wash-a` / `--chip-hairline-a`); on hover a 1px conic rim (`--chip-ring-a` 0.9 light / 0.58 dark — a 1px line needs more saturation than a card-wide rim) spins on the registered `--chip-ang` for 5.5 s, two 1px stars inside the pill twinkle at 1.7 s, and the label steps to `--accent-strong` (5.04:1 light, 13.6:1 dark). The old 20–24 % `--wash-*` fill is gone: three hues spread across ~48px do not separate, so the pill read as one dirty block. The stars paint at `z-index: -1` under `isolation` — above the wash, never over the glyphs; `prefers-reduced-motion` stops the spin and the twinkle and keeps the static ring. Specimen in `/UI` section 05. **`.eyebrow` is not uppercase and is not letter-spaced** — the labels are Chinese, where both only hurt legibility, and a tracked all-caps eyebrow over every heading is the most templated-looking device on the web right now.

**The living UI standard is a route, not a document.** `/UI` (`src/app/UI/page.js`) renders the palette, type ladder, radii, shadows, motion tokens, component gallery and the live card-hover demo. It ships no colour or size of its own: `src/lib/css-probe.js` walks the stylesheets, rebuilds `:root` and `.dark` as two self-contained scopes on the page, and reads every value with `getComputedStyle`, so editing `globals.css` updates the page with no second edit and the light/dark panels stay correct even while the page itself is in the other theme. The only per-token maintenance is one row in the page's `GROUPS` arrays (token name + purpose); a deleted token shows as "读取中…" instead of silently drifting. The path is uppercase `/UI` because the folder is `UI`, and a case-only `/ui` redirect is impossible here — Next matches redirect sources case-insensitively, so a `/ui → /UI` rule also matches `/UI` and loops (`ERR_TOO_MANY_REDIRECTS`). Keep new components in that gallery: the rule is "specimen first, then the real route".

Shared UI primitives: `card.js` (hairline ring + hover lift; used by home, `/blog`, `/tags/*`, related posts), `tag-chips.js` (responsive +N collapse, expand-in-place), `modal.js` (+ `rss-modal.js` / `email-modal.js`, both copy-to-clipboard with manual-copy fallback), `search-grid.js` (shared search + load-more list), `skeletons.js` (the Suspense fallbacks for the three params routes — static, `aria-hidden`, no shimmer). Custom `.prose` overrides in globals.css must keep their `:not(.not-prose *)` guards or they leak into card UI.

**Post images carry their real intrinsic size.** `rehype-figure` reads each local file's width/height with `sharp` at render time (cached per process) and writes `width`/`height` onto the `<img>`; `OptimizedHTMLRenderer` passes them to `next/image`. This used to be hard-coded `1920×1080` for every image, so a 4:3 screenshot reserved a 16:9 box and the article reflowed as the bitmap arrived (measured 639×360 → 639×510 mid-scroll). The **first** body image additionally gets `loading="eager"` + `fetchPriority="high"`; everything below stays lazy. If a file cannot be read, the attributes are simply omitted and the browser falls back to its own behaviour — this is an enhancement, never a build gate.

**Pointer-tracked cards** — `<Spotlight />` mounted once in `layout.js`, `spotlight.js`. One delegated `pointermove` listener (not one per card) writes `--spot-x` / `--spot-y` (percentages) and `--spot-ang` (degrees from the card centre) onto the hovered `.card-spotlight`, and the CSS does the rest: `.card-interactive:hover::before, .card-interactive:hover::after { opacity: 1 }` reveals the rim and the glow at the values the script last wrote. The listener updates on **every** move inside a card (an early `card === current` guard made the decoration freeze where the pointer crossed the edge — that was the reported "it doesn't follow"), coalesces writes into one `requestAnimationFrame`, and caches the card rect until scroll/resize, since `getBoundingClientRect()` per move forces a layout read. Two `@property` registrations (`--spot-x` / `--spot-y` as `<percentage>`, both `inherits: true`) make the glow **ease** to the pointer (140 ms linear) instead of teleporting; the transition is declared on `.card-spotlight::after`, where the values are consumed. `--spot-ang` is deliberately **not** registered: a conic gradient is 360°-periodic, so easing an angle across the ±180° wrap would spin the rim a whole turn. **The registrations must stay outside `@layer components`; a registered declaration inside a layer is not emitted.** Both pseudo-element layers are `z-index: -1` under `isolation: isolate` on the card (above its background, below its text, and *below* the title's `after:inset-0` stretched link — do not give children `position: relative`, it shrinks the click target to the title). `prefers-reduced-motion` needs no rule here: the angle is instant and the glow is a 140 ms property transition on a 0.24-alpha tint.

**Do not write `-webkit-backdrop-filter` by hand.** Lightning CSS drops the standard `backdrop-filter` when the prefixed form is also present in the source, which silently killed the sticky navbar's blur. Declare only `backdrop-filter`; the prefix is emitted automatically.

**Theme toggle**: `themeswitch.js` wraps the swap in `document.startViewTransition` with a circular `clip-path` reveal (0.618 s) and adds `.theme-vt` for its duration. `clip-path` is not composited, so the smoothness comes from making the reveal the *only* animation running: `html.theme-vt * { transition: none !important }` suppresses every Tailwind `transition-colors`/`transition-all`, which would otherwise crossfade the same theme tokens underneath it. The block also drops the sticky navbar's `backdrop-filter`. `.theme-vt` is removed in `.then(ok, err)` (not `.finally()`-style success-only) so a rejected transition cannot leave it stuck and freeze every transition site-wide. Measured via `document.getAnimations()`: 0 CSSTransitions mid-reveal with the rule, 561 without.

**Route transitions**: every page wraps its content in `<RouteTransition>` (`src/components/route-transition.js`), a `react` `<ViewTransition exit="page-exit" enter="page-enter-fade" default="none">`. **Both halves are named, and both are animated from the view-transition snapshots, not from the live DOM.** That split is the point: an enter animation on the live tree only runs if React unmounts and remounts the element, and React reuses a node of the same type in the same position — so an exit can run with no matching entrance. A `::view-transition-new` snapshot is created for every transition that produces new content, so that half cannot be skipped. `.page-enter` remains, but as the **first-paint** fade only (a first paint is not a Transition and gets no snapshot); it is also what `PageTransition` emits, and `/blog/[...slug]/page.js` uses the class directly.

Timings are deliberately unequal — `::view-transition-old(.page-exit)` runs `page-fade` **150 ms** reversed, `::view-transition-new(.page-enter-fade)` runs `page-enter-snapshot` (opacity + a 6 px rise) for **260 ms**. Equal durations put both layers at ~50 % opacity at the midpoint, which reads as a wash; the shorter exit makes it a handoff. The 6 px transform is safe **only** on a snapshot pseudo-element — a transform on real DOM creates a containing block and would break `position: sticky` descendants (the homepage's pinned search bar), which is why `PageTransition` stays opacity-only.

CSS lives in `globals.css` next to the theme block. Two details there are load-bearing: `::view-transition { pointer-events: none }` (the snapshot overlays the live page and would eat the reader's next click), and `html:not(.theme-vt)::view-transition-old(root) { animation: none }` — the UA cross-fades the root on *every* view transition, which double-animates a route change; the theme toggle has its own root rule and so is excluded rather than overridden. The navbar and footer sit in `layout.js` *outside* `<main>`, so they are outside every page snapshot and hold still while the content crossfades — the nextjs.org arrangement. Measured with `document.getAnimations()` on `/blog` → post: one `page-fade` at 150 ms on `::view-transition-old`, one `page-enter-snapshot` at 260 ms on `::view-transition-new`, no `old(root)` fade.

**There is deliberately no `loading.js`.** Every route here is static and prefetched, so a navigation resolves in the same commit as the click and there is nothing to suspend on — the fallback could never legitimately show. Measured: adding one for `/blog` moved the real page into `<div hidden id="S:0">` behind JavaScript (+1.0 KB gz on `/blog`, +3.0 KB gz on a post page) with **no `<noscript>` fallback**, so a JS-less reader got skeletons instead of the article. The Next 16 docs agree it is the wrong tool twice over: `prefetching.md:59-62` says a route *with* a `loading.js` prefetches only "layout to first loading boundary" and its client cache TTL drops to "off by default", where a route without one prefetches the "entire page" for 5 minutes — so adding one would cancel the prefetch and then hide the round-trip it creates. Do not re-add one without re-measuring.

Tags: canonical slugs are English (15-tag taxonomy), Chinese display labels live in `data/tagLabels.js`. Tag URLs are `/tags/<EnglishSlug>`; `/tags/Web3` permanently redirects to `/tags/Crypto` (`next.config.js` redirects).

## Rendering model (Cache Components)

`next.config.js` sets `cacheComponents: true`. In Next 16 that mode is not a switch on top of the old model — it changes what renders are *allowed* to do:

- **No synchronous IO during prerender.** `new Date()`, `Math.random()`, `Date.now()` and `cookies()`/`headers()` throw at build time with `blocking-prerender-current-time`. The fix is never to move the page to request time; it is `'use cache'` + `cacheLife()` around the read, which captures the value at a build/revalidation boundary. `src/lib/site-year.js` is the canonical example (footer year, `cacheLife("days")`). `sitemap.js` does the same and, because a clock read there was also meaningless, derives per-route `lastModified` from frontmatter instead.
- **Anything request-bound must sit behind `<Suspense>`** or it blocks the static shell. The navbar's `NavList` (a `usePathname` client component, split into `nav-links.js`) is wrapped for that reason; `Lightbox` no longer needs a boundary because it reads no router state — it is mounted directly and its viewer chunk is imported on intent.
- **A page whose first statement is `await params` has no static shell.** Partial Prefetching renders one URL-independent App Shell per route, so awaiting `props.params` before any URL-independent content fails `next build` with `blocking-prerender-dynamic` (or `instant-shell-url-data` at runtime). The three dynamic-param routes are solved the same way, and the shape is worth copying:

  1. The route component is **not async** and renders the URL-independent frame first (grid, asides, transitions). It passes the `params` *promise* — not the awaited value — down.
  2. An inner async component awaits it inside `<Suspense fallback={<ArticleSkeleton />}>`.
  3. The content read itself goes through `src/lib/content/cached.js` (`getCachedPost` / `getCachedPage` / `getCachedPosts`, each `'use cache'` + `cacheLife("max")`, keyed by slug). That is what keeps Shiki out of the request path and lets the Suspense hole resolve as a cache read.

  These routes report `◐` in the build table: static shell plus a streamed hole. `◐` for a params route is the expected result, not a regression — do not "fix" it with `export const instant = false`, which drops the prerender entirely and makes the route request-rendered.
- **`runtime` route segment config is rejected** — do not add `export const runtime = "edge"`. `/og` is a Node function by nature (it reads the avatar from disk).
- Routes fall into three buckets in the build table: `○` fully static, `◐` partially prerendered (static shell + streamed dynamic holes, e.g. `generateStaticParams` routes), `ƒ` on demand (feeds, `/og`). Prefer `○`; a route that drifts to `ƒ` is usually an accident.
- `partialPrefetching: true` is set explicitly because it is **not** implied by `cacheComponents`: unset behaves like `false` and logs a warning in 16.3+. With it on, each route prefetches a URL-independent App Shell, so content that depends on `params`/`searchParams` resolves after navigation.
- **Each prerendered route opts into the 16.4 guarantees explicitly**: `export const instant = true` (dev-only validation that the route's shell resolves synchronously) and `export const ensureStatic = "shell"` (build fails if the App Shell would become request-rendered). They sit on the seven page routes; `"shell"` passes today, and it is the guard against a future edit that quietly turns a static page into `ƒ`. Do not delete them to silence a build failure — a failure there means a shell regressed.
- `next.config.js` sets `deploymentId: process.env.VERCEL_DEPLOYMENT_ID`. Next 16 uses it to scope client router caches and prefetch entries to a deploy, so a stale client cannot navigate into HTML from a previous deployment.
- The three params-route Suspense fallbacks in `skeletons.js` are `min-h-dvh`. Without that they were shorter than the viewport, so when streamed content replaced the shell the footer was pushed ~20 000 px down and CLS measured **0.207** on a post page (single shift, t ≈ 723 ms, `FOOTER`'s rect moving) and 0.107 on a tag page. `min-h-dvh` reserves the fold; both routes now measure 0. This is a CLS fix, not decoration — do not remove it, and keep new skeletons in the same shape.
- Friend links are **rotated on the server** (`src/lib/rotation.js`: day index inside a `'use cache'` + `cacheLife("days")` scope) instead of shuffled after mount. The old effect reordered the grid post-hydration to give every friend the top slots; that is a layout shift by construction and measured **CLS 0.099 on /links** (one shift, source = the card link), plus a hydration mismatch. Rotation keeps the fairness, costs no client JS and shifts nothing. `friendlinks.js` is a Server Component as a result.
- Scroll-driven UI is CSS where possible: the floating back-to-top controls are `.scroll-actions` with an `animation-timeline: scroll()` fade (no scroll listener, no state), and the reading-progress bar is the same mechanism. `scroll.js` only calls `scrollTo()` and honours `prefers-reduced-motion`. React state for "have we scrolled 120px" was a per-frame re-render on every route.

DOM code must scope its queries: React's `<Activity>` keeps navigated-away routes mounted but hidden, so `Lightbox` scans `main img.lightbox-image` and `toc.js` scans `main article`. A `document.querySelectorAll("img")` would pick up another page's DOM.

## Open Graph card

`src/app/og/route.js` renders a 1200×630 light-mode card with `next/og` (Satori). Query params carry everything the card depends on — `title`, `date`, `read`, `tags` — which is what makes `s-maxage=31536000, immutable` safe: a content edit produces a different URL. Call sites build it with `URLSearchParams` (see `src/lib/feed/urls.js`).

Constraints worth knowing before editing it:

- **Satori is not a browser.** Flexbox only (no grid, no `filter: blur` — the blooms are stacked radial gradients), and every element with children needs explicit `display: "flex"`.
- **The palette is hard-coded in the file**, because Satori resolves inline styles outside the document and cannot read CSS custom properties. Keep it in sync with `:root`.
- **The avatar is read from disk and resized by `sharp` at runtime** to a 152 px PNG data URI. Passing the original 871 KB file would blow the 500 KB function bundle; `outputFileTracingIncludes` in `next.config.js` is what makes the file present in the deployed function at all. Any failure degrades to an initial-letter avatar rather than failing the card.
- **Fonts are fetched per card** as a Google Fonts `text=` subset built from the exact glyphs drawn, so a CJK face costs KBs, not MBs. A weight that fails to load is dropped, not retried.
- Post cards show date, reading time and up to 3 tag labels + a `+N` chip; page cards hide the date/tag rows and centre the title. Both always carry blog name, domain and author.

## Routing overview

- `/` — home (`src/app/page.js`): featured grid + Latest/tag/Search tabs (client-side `Articles`, load-more in batches of 8) + about/microblog sidebar (the terminal / 随想 block is gone).
- `/blog` — archive with tag sidebar, site-wide Fuse.js search and load-more (numbered pagination removed; `/blog/page/*` redirects to `/blog`).
- `/blog/[...slug]` — a post. Matches via `post.slugAsParams` against `getPosts()`; includes related posts (`lib/related.js`: tag overlap + recency, excludes prev/next) and a CSS scroll-driven reading-progress bar. The right rail pins the **outline**, not the author card: `AboutMe` sits in normal flow so it scrolls up and away, and `.toc-panel` is the sticky element (a direct child of the `aside`, because the grid row is full article height — nested one level deeper its sticky range would end at the card's bottom). `.toc-panel` also caps itself at `100dvh - nav` with internal scroll, since a sticky box taller than the viewport can never reveal its own bottom.
- `/[...slug]` — markdown pages (e.g. `/about`, plain markdown, no JSX). Matches via `getPages()`.
- `/tags/[...slug]` — tag pages, **statically prerendered** via `generateStaticParams` from `lib/tag-counts.js`; same cards/search/load-more as `/blog`. `getTagCounts()`/`getSortedTags()` are functions, not constants, for the same staleness reason as the loader.
- `/UI` — the living UI standard: palette / type / shape / motion / component gallery, all values read from the running stylesheet (see Design system). Static route, no data.
- `/microblog`, `/links` — microblog, friend links. `/microblog/rss` is a standalone RSS 2.0 feed for the microblog (full text + images via `content:encoded`, first image as enclosure).
- `/og` — Open Graph image, Node runtime, CDN-cached (see "Open Graph card" above).
- `sitemap.js`, `robots.js`, and the feed routes handle SEO/discovery; tag pages are listed in both.

## Conventions & gotchas

- JS (not TS) throughout; most imports are **relative**, even though `jsconfig.json` defines `@/*` → `./src/*` (the alias is currently unused).
- **Turbopack is required and `next.config.js` is plain** — no `withContentlayer` wrapper, no plugin. `next dev`/`next build` run directly against the app.
- Tailwind is **v4** (`@tailwindcss/postcss` + `@import "tailwindcss"` in `globals.css`) loading a minimal v3-style `tailwind.config.js` via `@config` (typography plugin + `darkMode: ["class"]`). All colors/radii/shadows/motion are tokens in `globals.css` `@theme inline`.
- `/_next/image` responses carry `Content-Disposition: inline` natively via `images.contentDispositionType` in `next.config.js` (Next's optimizer defaults to `attachment`, which makes direct opens download). There is no middleware and no vercel.json; don't re-add override layers.
- Analytics is self-hosted **Umami** (`src/components/umami-analytics.js`, config in `siteMetadata.umami`); it only loads in production, with `strategy="lazyOnload"` so it never competes with first paint. Comments are **Giscus**, split in two: `comments.js` is the lazy shell (`#comments` anchor, `min-h-[320px]` reservation, an `IntersectionObserver` with a 600px rootMargin) and `giscus-embed.js` is the widget, pulled in with `next/dynamic({ ssr: false })` only once the reader is near it. A third-party iframe on every article was the single largest avoidable cost on the article path; measured: 0 `giscus-widget` elements before scrolling, 1 after (and 0 requests to giscus.app on load). No observable/IO available falls back to a deferred mount, not to never.
- **Prefetching is a budget, not a default.** `<Link prefetch={true}>` is for the one link that predicts the next click: post cards, prev/next, the primary nav. Tag chips (`tag-chips.js`) and the 15-link tag sidebar (`bloglistlayout.js`) are `prefetch={false}` — a page of eight cards used to issue up to 24 tag-page prefetches for links nobody clicks, competing with the article prefetch that does predict the read.
- `images.minimumCacheTTL` is 31 days in `next.config.js`: optimized image URLs carry a content hash, and Next's 60s default re-runs the optimizer on every repeat view of an unchanged file.
- Search is **one site-wide Fuse.js implementation** (`src/lib/use-post-search.js`) over a build-time slim index `public/search-index.json` (`scripts/build-search-index.mjs`, gitignored, regenerated by `yarn build`/`dev`; the publish script whitelists the generator for the template). The index includes Chinese tag labels so CJK queries hit English tags. **Fuse and the index load on the first query, not on mount** — loading them at mount made every visitor download 40 KB of index plus the library while the page was still painting, for a feature most never use. The search inputs additionally call `warmSearch()` on `focus`/`pointerenter`: by the time a reader has clicked into the box, the index is already in flight, so the first keystroke filters instead of waiting.
- **Tag hygiene**: `node scripts/check-tags.mjs` (add `--json`) reports unknown tags (which would 404), single-tag posts, tags with fewer than three posts and the full distribution, from `public/search-index.json`. It is deliberately not wired into `package.json` — the publish script deletes `scripts/` apart from the search-index generator, so a shipped `check:tags` script would be a broken command in the template.
- **The lightbox is in-house and wired through CSS classes, not props**: `rehype-figure` tags every post image with `lightbox-image`, `OptimizedHTMLRenderer` preserves that class when swapping in `next/image`, and the root layout mounts `Lightbox` (`lightbox-controller.js`). One delegated `click` listener on `document` opens the viewer — no handler per image, no per-navigation DOM walk. The viewer component (`lightbox-viewer.js`, ~350 lines) is dynamically imported **on intent** (`pointerover`/`focusin`/`touchstart`), so a reader who never opens a photo downloads **0 bytes** of it; it replaces `yet-another-react-lightbox` (removed, −30 KB gz per post route) and keeps the features that library provided: prev/next, wheel/±/double-click zoom, drag pan, pinch, counter, caption, Esc, focus trap, scroll lock, background `inert` — all from `src/lib/overlay.js`. Dropping the `lightbox-image` class anywhere breaks it.
- **The open animation is a FLIP morph, not a View Transition.** `startViewTransition` was measured at **180-250 ms before it would even call the update callback** on an image-heavy post (the browser snapshots the whole page), which is exactly the "opens slowly" complaint — a route transition pays that cost once, a lightbox pays it on every photo. The controller captures the clicked thumbnail's rect and the viewer animates its image from that rect with the Web Animations API in the same frame. Measured cold/warm open: **214 ms first click (chunk fetch) / 22-30 ms after intent prefetch**, morph 300 ms, close immediate (a reverse morph has to stay mounted until it finishes; unmounting synchronously is what every viewer does and it can never stall). Speed of opening is the feature — do not reintroduce `startViewTransition` here without re-measuring.
- Dates are formatted with `src/lib/date.js` (Intl, zh-CN long form; Beijing time when a clock time is involved) and sorted with `date-fns` (`compareDesc`). Never reintroduce moment. Reading time is rendered by `readingTimeLabel()` (`约 N 分钟`) and the footer year by `yearInBeijing()` behind `getSiteYear()` — both live here so no component builds date strings inline.
- Shiki emits only `--shiki-light`/`--shiki-dark` vars (`defaultColor: false` in the pipeline); the active color is applied by CSS in globals.css.
- `data/.obsidian/` and `.obsidian/` are gitignored and must **never** reach the published template — they can carry plugin credentials (e.g. Livesync).
- `.next`, `.tmp`, and `public/search-index.json` are generated — never edit by hand.

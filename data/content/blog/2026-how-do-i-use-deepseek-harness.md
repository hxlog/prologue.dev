## 前言

先说下我对三大工具的理解：

| 工具        | 使用体验                                                                                                                                                 | 优势                                            | 劣势                                                                                                 |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Codex       | 功能较为全面，GUI友好，内置browser use、Office编辑等原生支持，整体使用体验综合了办公与代码场景，与此同时，今年Codex与ChatGPT的产品线与额度计费都融为一体 | 开箱即用，万金油，**应用场景多**，支持沙箱      | 搭配非OpenAI家的模型效果一般                                                                         |
| Claude Code | **大型项目首选**，CLI极简设计，专注于代码场景，支持Git Workflow，软件工程上较为严谨                                                                      | 搭配Claude Code自家Skills与模型使用体验是最好的 | 软件设计上最重，三大工具中占用最多上下文，Claude家模型贵、容易被封号，使用非Claude模型任务完成度一般 |
| Cursor      | **结合了传统IDE的优势，支持代码DIFF**，方便对AI生成的代码与变更进行Review和Merge，如果对AI自动改代码不放心，用它就对了，GUI友好                          | 与传统IDE结合，功能最为完整                     | Grok模型输出较为缓慢，订阅费用不菲                                                                   |

目前的Vibe Coding工具栈都优先适配自家模型做后训练，用非自家模型在`/goal`模式下会出现长任务会中途中断或直接放弃任务。

海外模型的试错与折腾成本太高，所以我在实际项目中基本都是用Deepseek V4.1 Flash 1017模型 和 Deepseek Harness（简称DSH）作为脚手架，我认为这是最适合学习与试错的架构，无需担心天价账单，可玩性高。实际上我还是有开IDE去看实际代码改动（实在是不放心，对模型没信心），AI一旦往错误的方向挖坑，必须及时提示，否则浪费时间和token。

## 基本概念

| 概念     | 描述                                                                                                                                       | 要点                                                                                                                                                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Skills   | 可以理解为**可智能路由、按需启用的提示词模板**，从而无需重复注入提示词                                                                     | 宁缺毋滥，skills最好是高度模板化且未被内化到模型能力层，例如“如何写一份报告”这样的skill可以被删除，过多的提示反而影响模型发挥，也就是思维链的冗余；相反，若是“软件著作权申请材料规范”的skill就非常有价值，所以优秀的skills最好是对特定场景有针对性，而非通用的、看起来啥都能干的 |
| MCP      | Agent上下文的API，为了获取更多可用数据                                                                                                     | MCP同样占用大量上下文，按项目级按需启用，MCP用于拓展特定领域的信息源，如召回公司财务、创新药管线、城市天气等最新数据                                                                                                                                                             |
| 联网搜索 | 可以理解成模型层的搜索引擎                                                                                                                 | 补充外部信息来源，拓展上下文，但互联网上的脏数据会影响任务交付程度，取决于模型层的数据质量，不同数据源差异较大                                                                                                                                                                   |
| Tools    | 模型与本地进行基本的交互，CLI命令行和JSON信息交互是最常见的，如powershell命令行、playwright前端浏览器测试、browser use插件、office编辑工具 | 要让Agent了解或能够感知到到当前本地的开发环境、依赖项，决定最终能用哪些工具，而不是模型到处试错碰壁，提前准备好需要用的开发环境                                                                                                                                                  |

不难看出，影响Harness Agent任务交付质量的因素非常多，模型层可能是其中方差较小的一环。

## 使用技巧

- Plan模式不是必须的，**大部分Harness软件给Plan模式设计时是只读权限，会影响持久化与思考深度**，对于长任务，多轮问答后生成Plan文档的效果更好，即先生成Plan与持久化记忆的上下文变成Markdown文件；
- Goal模式要讲清楚交付的目标或完成条件；
- 密码一定要用ENV环境变量，不要让模型直接读密钥；
- 沙箱和git worktree严谨的软件工程设计，但不是必须的；
- 不要让AI一上来就一把梭。用AI至少先描述背景、需求、改动方向，AI返回一版设计与需求方案，让AI反问自己对齐需求，再做MVP（最简可行产品）或demo，整体技术栈、主要功能的实现路线确定后，再形成最终版本的Plan，核对方案，再开启完全权限完成开发。尽可能避免让AI自己发挥，只让AI去做一些基础功能实现，不要让它发散思考，人工Review Plan，修订方案的收益是最大的，不可忽视；
- **不要在Agent完成最终产出后再去改，只会越改越多bug**，尽量在计划方案时就写清楚；
- 充分利用**代码规范、测试、CI/CD工具**，Pytest、Vitest、ESLint、Prettier，每完成一个功能实现务必增加一个测试案例来验证当前功能实现的路径，如果是数据抽取工作，那就要维护金标集，能尽可能避免AI生成bug；
- 必要时增加测试、验证、**对抗式生成检验**、审计；
- 新的前端项目最好先用Figma产出原型图，再用插件导入，再手动写需求文档（不需要很规范，但讲清楚每个功能的预期行为即可）；
- 模仿Claude Code的Ultra Code Workflows原理，拆解任务，**拆分多个不相互依赖的子任务给多个Agent并行开发**，大幅提高开发效率；
- **形成持久化记忆和知识库**，我用的是[阿里AgentScrope的ReMe](https://github.com/agentscope-ai/ReMe)，每个对话结束后就会总结形成带Frontmatter的日记，定期会整理记忆形成知识库，也就是这部分记忆会保持更新，新对话使用是用MCP的BM25或向量召回方式读取记忆加载到上下文；
- 遇到模型不擅长的非代码类的开发任务，可以适当下载基本相关的电子书、任务规范等，交给模型进行**蒸馏**、总结对当前项目有用的内容，并汇总成Markdown，再去执行Plan计划步骤，而不是让模型调用大量联网搜索找了更多无关紧要的文本。

## 量化想法验证

我花了一百亿的token快速验证（花了大半个月）加密货币截面多空多因子策略的可能性与有效性，我把任务分成以下过程：

- **接口调用、数据清洗与ETL**。经过对多个链上与连下降交易所做A/B测试得到binance家的行情数据信噪比更好的结论，分钟级数据近2TB，接入现货与期货数据，链上数据只接入了EtherScan，一次性补全历史数据并设置轮询，ETL落库到PostgreSQL + TimeScaleDB，前值Fill填充。这里就有第一个显而易见的坑，目前观测交易所上的币种都有幸存者偏差，无数的加密货币项目都走向死亡，如今能通过API查到的都是幸存者；
- **设计市场Beta**。让Agent跑了等权重、BTC唯一、BTC+ETH加权、全市场指数等数种方案作为Beta的候选组合，经过测算验证得到BTC+ETH加权的Beta刻画更好；
- **构建因子候选集**。用了三种因子构建的方法：一是本来就有微观市场逻辑的指标，如大户/全市场多空人数比、合约主动买卖价差比、基差、动量、反转、Beta、ln（市值）等，二是提供基础数据和算子，遗传算法组合，三是起模型去模仿第一种方法按照市场逻辑的语义和模型能力去写因子。根据Rank IC、IR去筛选；
- **特征选择**。用Lasso回归、PCA分析筛选有增量收益的因子，为了保证多个独立因子之间是相互独立，用层次聚类方法保留同一系列表现最好的数个，再剔除掉因子间相关系数高于0.7的，正交化；
- 预测什么？用T+N的K线收益率的截面Rank以及Alpha（剔除Beta）的截面收益率，实验发现预测后者效果更好；
- **训练方法**。LightGBM、XGBooster等决策树算法回测效果较好，反而用深度学习如TCN、LSTM效果不佳，找不到历史规律，[FreqTrade项目](https://github.com/freqtrade/freqtrade)中也提到过这个，面对信噪比极低的数据，GBDT模型表现确实更好；
- **回测**。有2021-2026的数据，那么将2021-2024作为训练集，2024-2025作为验证集，测算2026年至今的收益情况，尽管这不是真实的样本外回测，但也足够，中间还学习到组合对称交叉验证(CSCV)框架中的DSR（Deflated Sharpe Ratio，去膨胀夏普比率）、PBO（回测过拟合概率）等回测绩效衡量方法。
  （省略无数次返工与循环）
  回测结果是日均换手13%，2021-2024以及2026年的年夏普和Sortino都在1.5左右，但唯独2025年亏损（山寨币齐跌），但又将训练集往后挪，再观察2026年至今收益似乎又得到改善，这可能是币圈的周期比较长，数据集不够多，模型只学到了某种regime，结果应该是过拟合的。

还有一些在币圈比较可怕但又不得不考虑的事情：

- 合约插针扫损，如果在参数中加入止损回测结果大打折扣；
- 山寨币低流动性轧空，也就是很多散户看到的一个币可以一天涨几十个点的情况，只能通过流动性与合约数据剔除掉部分异常资金费率与流动性欠佳的币种；
- 滑点，流动性差的币种maker难成交，taker费用高，投资组合优化建议用成本感知方法，加入换手惩罚或换手率上限；
- 要给代币贴标签，如PoW、PoS、DeFi等，做工具变量，非常麻烦
- 大部分代币都会退市，消失，要维护黑名单

我认为必须从数据源做功课，互联网上可获取的免费、公开数据带来的Alpha增量很有限，有实质性增量Alpha或风险分散作用的因子也少。

最终的策略是能跑，但是它只是拟合历史大部分时间的周期与模式，加上我缺少PIT（Point in Time）的时点数据，怎么想都感觉不靠谱，还是要将数据层做好也行，数据脏那就去做数据治理。

这个项目先存档了，以后哪天有优秀的数据源再回来研究。

## DSH的插件开发

DSH的设计是“一切皆插件”，也就是它暴露基本功能的接口，但不像以上所说的工具一样直接把Skills、MCP、持久化、对话导入导出等功能做成GUI可开箱即用的程度，我为此根据Cursor的设计为DSH开发了两款插件：

- dsh-mcp-tools，类 Cursor 风格的全局 MCP 控制：自由添加、停用、删除 MCP 接口与工具，适合 MCP 测试、按需请求、拓展上下文等场景。

![dsh-mcp-tools插件，在设置中能管理用户的MCP Server，添加、删除、按需开关MCP，并查看MCP工具的介绍文本](/static/images/dsh-mcp-tools-screenshot.png)

[dsh-mcp-tools Github仓库](https://github.com/hxlog/dsh-mcp-tools)

- dsh-skills-tools，DeepSeek Harness 的 Skills 管理器。从 Git 仓库或本机目录导入 Agent Skills，按仓库分组管理，随时启用、停用、补齐和查看内容。

![dsh-skills-tools插件，在设置中能管理用户的Skills，添加、删除、按需开关Skills，并查看Skills的介绍文本，定期上游仓库检查更新。](/static/images/dsh-skills-tools.png)

[dsh-skills-tools Github仓库](https://github.com/hxlog/dsh-skills-tools)

可以直接在Deepseek Harness桌面版添加插件页面，输入dsh-mcp-tools或dsh-skills-tools就能直接安装获得和Cursor同款的GUI Skills与MCP插件。

## 怎样才能用好AI

我可能和大部分人想的不同，我认为用好Agent不需要刻意去学什么MCP、Skills、提示词工程，应该专注于：
- **认识完成一项任务的基本概念与方法论**，例如技术选型，要使用怎样的工具栈搭配；什么是BM25、TF-IDF、向量召回；UI的侧边距移动多少px/REM；诸如此类，掌握某种技术或工作流的集合符号；
- **理清需求与目标**，不需要写的很规范和宏大，想到什么写什么，模型会帮你理顺的，也就是提供当前任务的完整背景；
- **了解这个任务需要什么资源或支持**，提前装好需要的运行库与开发环境，装载对该任务有帮助的MCP和Skills，甚至蒸馏专业书籍与文章的知识，形成**长期记忆与上下文持久化**；
- **让模型专注于做完形填空**，也就是把完成这项任务所需的一切都喂到模型嘴边，而不是和一些小白一样幻想着几乎零样本提示对着AI许愿。
